## 1. Цели

Поведение «как в KSP», которое должно получиться. Критерии приёмки — в разделах 7 и 9.

1. Корабль состоит из деталей с геометрией. Каждая деталь — твёрдое тело со своей массой, инерцией и формой.
2. Детали соединены стыками с пределом нагрузки. Стык рвётся, когда нагрузка превышает предел.
3. Контакт с рельефом и постройками считается по точкам деталей, а не по одной точке центра корабля.
4. Опоры (ноги) пружинят с ограниченным ходом и затухающими колебаниями.
5. Корабль опрокидывается по геометрии при касании одной ногой и при тяге вне центра масс.
6. Отломок продолжает движение по физике, а не разлетается по заранее заданному шаблону.
7. Стоянка, вращение планеты и удалённость от начала координат не дают дрожания и взрыва.
8. Мягкая посадка из `Test29_DescentChain` остаётся мягкой посадкой. Это жёсткое требование на всех фазах.

## 6. Архитектура целевой модели

Эта часть сохранена из v1 с уточнениями по коду. Основные факты о текущей модели, проверенные по коду:

- Корабль — точка: `Spacecraft.Position, Velocity, Mass` в double.
- Полёт — DOPRI5 чанками и `AltitudeCrossingDetector.ForTouchdown` по высоте рельефа под центром корабля.
- Касание — `EventReactions.ApplyTouchdown`: нормаль `GetOutwardNormal`, при `|v_n| ≤ CrashToleranceMps` (5 м/с) режим Landed, иначе `JointedBreakup` (нагрузка `m·|v_n|/0.05 с` против `JointStrengthNewtons`).
- Посадка — `SurfaceMotion.Step`: точка на поверхности, трение `μs = 0.7`, `μk = 0.5` (из `BodyAuthoring`), перенос с вращением (`CoRotate`, `Slide`).
- `Parts` в сцене пуст (`Parts: []`), поэтому разрушение идёт по фолбэку `SingleThresholdBreakup`: 10 фрагментов, разлёт по золотому углу.
- Тяга: `ThrustSource` с направлением по умолчанию `(1,0,0)` в инерциальном кадре. `AttitudeSnapshot` нигде не задаётся.
- `AttitudePhysics` (RK4, шаг 0.02 с) нигде не создаётся вне тестов.
- `GetOutwardNormal` усредняет уклон примерно по 114 м и стоит 3 вызова высоты и 3 вызова `GetSurfaceState`.

### 6.1 Режимы

- **Orbit.** Как сейчас: точка, DOPRI5, события SOI, атмосферы, эфемерид.
- **Contact.** Включается, когда нижняя точка любой детали ниже `H_enter` над поверхностью (по умолчанию 300 м) или контакт предсказан в пределах 1 с. Выход — выше `H_exit = 400 м` без контактов (гистерезис). Фиксированный шаг решателя. Все детали — тела с формой. Учитывается аэродинамическое сопротивление по деталям (`площадь × Cd × q`).
- **Landed (сон).** Все детали в контакте, `|v| < 0.01 м/с`, `|ω| < 0.001 рад/с` в течение 0.5 с подряд. Физика спит. Пробуждение: тяга больше нуля или внешний импульс.

Переходы сохраняют позицию, скорость, ориентацию, угловую скорость и массу. Переход Orbit → Contact пересчитывает состояние из инерциального кадра в кадр поверхности (6.2).

### 6.2 Система отсчёта

- Решатель работает в кадре, жёстко связанном с телом: начало в центре тела, вращение с угловой скоростью тела. Поступательная скорость тела вычитается, поэтому скорости хранятся относительно поверхности. Так же устроен `SurfaceMotion`.
- Ускорение в этом кадре: `a = g − ω×(ω×r) − 2ω×v_rel` плюс тяга и сопротивление. Совпадает с `SurfaceMotion.FreeAcceleration`.
- Относительные скорости решают проблему шума при орбитальной скорости около 3·10⁴ м/с. Пороги `1e-9` в `SurfaceMotion` введены именно из-за этого.
- Переход в мировые и render-координаты — только на границе (`ShipView`, `FloatingOrigin`).

### 6.3 Модель тела и стыков

```csharp
public sealed class PartBody {
    public string Name;
    public double Mass;                    // кг
    public Matrix3x3 InertiaBody;          // в осях детали, относительно её ЦМ
    public Vector3d Position;              // ЦМ детали, кадр решателя
    public Vector3d Velocity;              // относительно поверхности
    public QuaternionD Orientation;        // body -> кадр решателя
    public Vector3d AngularVelocityBody;   // в осях детали
    public ConvexShape[] Shapes;           // выпуклые хуллы в осях детали
    public bool Alive = true;
}

public enum JointKind { Rigid, Spring }    // Hinge — позже

public sealed class Joint {
    public int A, B;                       // индексы деталей
    public Vector3d AnchorA, AnchorB;      // точка стыка в осях каждой детали
    public JointKind Kind;
    public double BreakForceN;             // предел силы, Н
    public double BreakTorqueNm;           // предел момента, Н·м
```

Описание корабля хранится в данных (ScriptableObject или JSON). Существующий `PartDefinition` расширяется полями формы, ориентации, `EngineOffset`, стыков и пределов разрыва. Пустой `Parts: []` в сцене заполняется тестовым аппаратом (раздел 8).

Масса, центр масс и тензор инерции считаются из геометрии. `AssemblyStats` сохраняется: для точечных деталей результат должен совпадать с прежним (`Test30_PartsTrap`).

### 6.4 Контакты с рельефом

Точки опроса детали: вершины выпуклого хулла, лежащие ниже уровня, плюс точки на плоском дне. Для ступни — сетка 3×3 на нижней грани. Типично 4–16 точек на деталь, до 64 на аппарат.

Для точки `p`: широта и долгота через `body.SurfaceLatLonAt`, высота `h = ITerrainModel.GetHeightMeters(lat, lon)`. Это та же функция, что использует физика сейчас. `TerrainModifier` (ровные площадки) учитывается автоматически.

- `depth = (R + h) − |p|`. Контакт при `depth > 0`.
- Нормальная сила: `F_n = max(0, k·depth − c·v_n)`. Параметры `k` и `c` задаются для контакта с землёй.
- Трение: `|F_t| ≤ μ·F_n`, `μ` из `SurfaceStaticFrictionMu` и `SurfaceKineticFrictionMu`. Переход покой/скольжение — как в `SurfaceMotion`.

**Нормаль.** `GetOutwardNormal` намеренно усреднён по 114 м, чтобы мелкие детали не дёргали здания (см. комментарий в `SurfaceGrounded`). Для ног и камней это неверно: нога на камне получит нормаль склона. Нужна вторая функция:

- `GroundNormalLocal(p)` — по 3–4 точкам на расстоянии `NormalFootprintMeters` (по умолчанию 0.5 м) вокруг `p`, с той же функцией высоты.
- `GetOutwardNormal` не менять: его используют посадка и постройки.

**Стоимость.** На 64 точках при шаге 1 мс `GetOutwardNormal` слишком дорог. Варианты, выбирать по профилированию:

1. Кэш. Высота и нормаль по точкам обновляются раз в 5–10 мс и линейно интерполируются. Первая версия делается этим способом.
2. Локальная карта высот в касательной плоскости: сетка 0.25 м на ±32 м вокруг аппарата, пересчёт при сдвиге больше 4 м или раз в 0.1 с, в Burst-джобе.

### 6.5 Контакты с постройками (SiteBox)

- Для деталей, способных столкнуться с постройкой, нужны выпуклые хуллы в их осях. Хуллы запекаются (раздел 9, риск 4).
- Глубина и нормаль для пары (хулл детали, хулл постройки) — через `Physics.ComputePenetration` в локальных координатах обоих (так уже сделано в `SiteBox.PushOutMesh`) или через GJK/EPA. Выбор — агенту, с тестом.
- Вогнутые постройки — набор боксов, механизм вокселизации уже есть в `SiteBox`.
- Контакт деталей одного корабля отключён для пар, связанных стыком.

### 6.6 Решатель

Рекомендуется XPBD (Macklin, Müller, Chentanez, 2016) для стыков и контактов. Метод устойчив при фиксированном шаге и не требует тонкой подгонки жёсткостей.

Один подшаг:

1. Интегрировать скорости: `v += (g_фиктивные + F_тяги + F_сопр) / m · dt`.
2. Предсказать позиции `x* = x + v·dt`. Ориентация — интегрированием кватерниона по ω.
3. Сгенерировать контакты по `x*` (6.4, 6.5).
4. Итерации (4–8): коррекция `x*` по ограничениям стыков и контактов с податливостью `α`. Трение — отдельной итерацией.
5. `v = (x* − x) / dt`. Из поворотов получить ω. Обновить `x`.
6. Силу в стыке получить из множителя ограничения: `F = λ / dt²`. Нужна для разрыва (6.9).

Жёсткие стыки: `α = 0`. Подвеска: `α = 1/k`.

Шаг по времени: 1 мс по умолчанию. Проверка: `dt ≤ 0.2 · √(m_min / k_max)` и тест энергии покоя (`Test213`).

**Время привязано к игровому времени, а не к кадрам.** Сетка подшагов `t_k = k·dt`. Кадр только продвигает решатель до нужного момента. Тогда результат не зависит от частоты кадров при одинаковом вводе (`Test280`).

### 6.7 Ноги и подвеска

- Нога = дочерняя деталь и Spring-стык. Ось стыка вдоль ноги, ход `[min, max]`, жёсткость `k`, демпфирование `c`.
- Стопа — выпуклый хулл (сфера или диск) в конце ноги. Контакт по нижней грани.
- Жёсткость под осадку: при весе `W` на `N` ногах и осадке `s` жёсткость одной ноги `k = W / (N·s)`. Пример: `W = 49 050 Н`, `N = 4`, `s = 0.25 м`, `k ≈ 49 кН/м`.
- Демпфирование: `ζ = 0.3–0.5`, `c = 2ζ·√(k·m_ноги)`.
- Корпус не касается земли при полном ходе ног. Если касается, это авария, обрабатывается контактом корпуса.

Урок KSP: там ноги колеблются и взрываются, потому что демпфирование подобрано плохо. Тест на затухание обязателен (`Test221`).

### 6.8 Тяга и ориентация

- Ориентация аппарата — кватернион решателя. В контакте передаётся в `ThrustSource.AttitudeSnapshot`, `BodyThrustDirection` задаёт ось двигателя. Так уже сделано в тестах `Test31_TorqueLink`.
- Точка приложения тяги — позиция двигателя-детали (новое поле `EngineOffset`). Момент `(r_двигателя − r_ЦМ) × F`. Сейчас тяга направлена по фиксированной инерциальной оси и приложена к центру масс.
- Вне контакта ориентация интегрируется `AttitudePhysics` (RK4). Правило: в контакте работает решатель, на орбите — `AttitudePhysics`. При переходах копируются ориентация и угловая скорость. Два интегратора вращения одновременно не держать.
- Расход топлива: пока общий массовый расход из `ThrustSource`. Распределение по бакам — позже.

### 6.9 Разрушение

- `JointedBreakup` заменяется разрывом по нагрузке решателя. Если `|F|` стыка больше `BreakForceN` или `|M|` больше `BreakTorqueNm`, стык удаляется и граф делится на острова.
- Превышение должно продлиться 2 подшага подряд, иначе одиночный численный выброс даст ложный разрыв (`Test252`).
- Отломок — отдельный остров тел с собственной физикой. Золотой разлёт не нужен: скорости физические.
- Импульс острова сохраняется (`Test251`).
- Мягкая или жёсткая посадка определяется не только скоростью центра, но и тем, разорвался ли стык и с какой нагрузкой. `CrashToleranceMps = 5 м/с` остаётся порогом аварии по скорости корпуса.

### 6.10 Обломки

- Обломки в контакте — острова решателя.
- Вне контакта — баллистика `DebrisPool`, как сейчас.
- При входе обломка в `H_enter` он переходит в решатель с тем же состоянием (`Test253`).
- Пул на 256 слотов сохраняется. Число тел в решателе ограничить (например, 32), остальные держать баллистикой.

### 6.11 Рендер

- `ShipView`: отдельный Transform на каждую деталь. Позиция — `ToRender(мировое положение детали)`, поворот — `AstroFrame.ToSimulation(ориентация)`.
- Мировое положение детали = положение тела + поворот планеты × позиция в кадре решателя. Тот же путь, что `SurfaceMotion.CoRotate`.
- Unity-коллайдеры для аппарата не нужны. Состояние аппарата не хранится в Unity-физике.

### 6.12 Время и варп

- В контакте варп ограничен. Сейчас есть `WarpController.AtmosphereMaxWarpFactor`. Решатель догоняет реальное время подшагами: при варпе ×4 и шаге 1 мс на кадр 60 Гц приходится около 67 подшагов.
- Рекомендуется сбрасывать варп при входе в контакт, как сейчас делается в атмосфере.
- Ввод (тяга, газ) меняется на границах кадра. Это допустимо. Детерминированность относится к последовательности подшагов при одинаковом вводе.

### 6.13 Переходный период: двухрежимность

Чтобы baseline оставался зелёным, новая модель вводится за переключателем `ContactModel: Legacy | Contact`.

- До гейта фазы 5 — `Legacy` по умолчанию. Все существующие кейсы идут по старому пути.
- На гейте фазы 5 — `Contact` включается для стенда и для игры. `Legacy` остаётся до конца фазы 7.
- Удаление `Legacy` (`SurfaceMotion`, `JointedBreakup`, `TryLiftoff` как путь посадки) — только после переписывания соответствующих кейсов из раздела 3.3 и записи в журнал изменений.

## 9. Риски и подводные камни

1. **Нормаль рельефа усреднена по 114 м.** Для ног и камней нужна локальная нормаль (6.4). Общую функцию не менять: её используют здания и посадка.
2. **`GetOutwardNormal` дорогой** (3 высоты и 3 `GetSurfaceState`). На подшаге 1 мс без кэша недопустим.
3. **Меш рельефа грубее функции.** В `SurfaceRoad` есть комментарий: «на склоне, где меш рельефа грубее точной функции высоты». Аппарат будет утопать или парить относительно видимой земли. Решение: `Test270` и повышение LOD рядом с аппаратом.
4. **Коллайдеры SiteBox по умолчанию — габаритные боксы на каждую деталь LOD0.** Для ног это даст невидимые стены. Нужны запечённые выпуклые хуллы (`BakedParts`, `UseConvexMesh`). В префабе площадки этих данных нет. Запекать через существующий `Editor/SiteBoxBaker.cs`.
5. **`Physics.ComputePenetration` молча не работает с невыпуклыми мешами** (комментарий в `SiteBox`). Все хуллы должны быть выпуклыми.
6. **Мировые скорости около 3·10⁴ м/с.** Пороги порядка `1e-9` и вычитание больших чисел дают шум. Все величины контакта считаются относительно поверхности.
7. **Варп и подшаги.** При варпе ×4 и шаге 1 мс на кадр приходится около 67 подшагов. Варп в контакте ограничивается.
8. **Тяга направлена по фиксированной инерциальной оси** `(1,0,0)`. Понятия «носа ракеты» в игре нет. Исправляется в фазе 8.
9. **`AttitudePhysics` и `ReactionControl` не подключены в игре.** Не удалять: они нужны для орбитального режима и покрыты тестами.
10. **`JointedBreakup` имитирует разлёт золотым углом.** Его инварианты импульса — образец для новых тестов. Сама модель заменяется.
11. **Стенд не содержит игровой цикл.** После шага 0.3 `SimulationRunner` не компилируется в стенде. Без шага 0.4 трейсы не могут идти через реальный код.
12. **Медленный набор.** `Test29_DescentChain` помечен как slow, но выполняется за ~1 с. Категория задаётся по набору и не отражает время. Гейт фазы 0 требует полного прогона slow и записи времени каждого кейса.
13. **Точечная масса в `SpacecraftPhysics`.** Остаётся для орбиты. Когда аппарат состоит из деталей, полная масса в орбитальном интеграторе должна равняться сумме масс деталей, иначе возникнет рассогласование.
14. **Игрок.** `SimulationRunner.StepPlayerSurface` ходит по функции высоты и выталкивается из `SiteBox`. В первой итерации не трогать. После фазы 6 можно сделать игрока пассажиром аппарата.
15. **Windows-артефакты в репозитории.** `bin/`, `obj/` и логи в UTF-16 могут ломать сборку и поиск. Шаг 0.1.
16. **NuGet в CI.** Без доступа к `nuget.org` `dotnet test` не запускается. Нужен доступ или локальный фид.

## 10. Что нельзя ломать

- Double-точность в состоянии симуляции. Float только для рендера.
- `FloatingOrigin` и `AstroFrame` — граница между физикой и движком.
- Орбитальный DOPRI5 и события: SOI, атмосфера, эфемериды. Все кейсы из раздела 3.1 и группы орбиты.
- Детерминированность: одинаковый ввод даёт одинаковый результат. Состояние аппарата не считается в Unity PhysX.
- Контракт `ITerrainModel`: высота и нормаль выводятся из одной геометрии. Новая локальная нормаль должна выводиться из той же функции высоты.
- Единый источник рельефа. `TerrainModifier` учитывается автоматически, потому что меняет функцию высоты.
- Мягкая посадка из `Test29_DescentChain`. Её исход — жёсткое требование на всех фазах.

## 13. Справка: как устроено в KSP

Кратко, по исследованию модмейкеров KSP 1.12.5 и документации Unity.

- Каждая деталь — Rigidbody. Стыки — joint'ы, которые могут разрываться по нагрузке. Физика закручивает эти стыки при посадке, и деформация не сохраняется в сейве.
- Рельеф — mesh-коллайдеры квадов самого высокого уровня рядом с кораблём.
- Постройки и взлётно-посадочная полоса — отдельные статики с собственными коллайдерами.
- Плавающее начало координат сдвигает мир. Krakensbane сдвигает систему отсчёта физики для быстрых кораблей.
- Выпуклые коллайдеры — ограничение PhysX. Не-выпуклые не сталкиваются между собой, и детали проходят друг сквозь друга.
- Штатные колёса KSP проблемны. Моды пишут свои wheel-коллайдеры. Урок: демпфирование опор нужно подбирать явно.

Что берём: состав из деталей, стыки с пределом нагрузки, контакты по точкам, плавающее начало, выпуклые хуллы.
Что не берём: PhysX для состояния аппарата, потому что это ломает детерминизм.
