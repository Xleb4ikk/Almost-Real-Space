# BACKLOG — RKN12 bake

Идеи **вне** TASK_RKN12. Не реализовывать в рамках задания.

## B-RK1. Пересмотр бюджета квантования BG3 (RQ4)

R0: доставленная ошибка Луны 4-тельного пресета на 10 годах против dd-Taylor —
**1.2187 м** при `QuantBudgetMeters = 2` (гарантия BG3 ≤ budget/2 = 1 м на
координату). Ошибка интегратора DOP853 при 900 с на порядки меньше; узкое место —
квантование коэффициентов. R3 требует ≤ 1 м на тело. Тюнинг `Degree`/segment/
`QuantBudgetMeters` в этом задании запрещён (RQ4) — вопрос выносится владельцу
отдельно, после RKN12.

## B-RK2. Dense/checkpoint-выход у dd-Taylor reference

`RunTaylorNBodyDdOptSeconds` возвращает только конечное состояние. Для плотного
независимого сравнения на узлах приходится либо перезапускать интегрирование на
каждое время, либо ограничиваться endpoint. Идея: добавить в reference сэмплирование
из ряда Тейлора (как в `TaylorNBody.RunSeconds`) — ускорит R3/R5 и будущие задачи.

## B-RK3. Диагностика P/COM внутри bake

`BakedEphemeris` хранит только смещения относительно родителя и не хранит
состояние корня. Поэтому по доставленным файлам нельзя измерить импульс/COM
(корень восстанавливается из COM=0 тождественно). Для гейтов §6.6 нужен лог
`RunBake` (in-process), а не пост-фактум чтение файлов. Это часть R2, но
постоянный диагностический блок в проде — отдельная идея.

## B-RK4. IAS15 / другой метод для 1 м на 100–1024 годах

R3/B-пробы: 1 м на 1024 годах требует dd force + h≈2.6 тыс. с (~12.4 млн
шагов, ~60 с 2-body) против 19.5 с у DOP853; dd state без dd force даёт 9–21 м.
Если 1 м обязателен — нужен IAS15/другой метод (вне TASK) или пересмотр
порога/формата (C). Не реализовывать в этой ветке без отдельного решения.

## B-RK5. Time-base в DOP853-пути

R3 показал, что `t += h` на 3.2e10 с даёт 0.5006 с за 642k шагов. В RKN12-ветке
это исправлено Kahan; DOP853-путь заморожен бит-в-бит и не менялся. Если
владелец захочет уменьшить 206/313 м на 1024 годах у DOP853 — это отдельное
решение, меняющее sha256 всех bake-файлов.
