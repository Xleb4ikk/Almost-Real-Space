## 1. Цель

Построить **изолированный стенд квалификации методов интегрирования**: консольный прогон без Unity
и без `StarSystem`, который прогоняет **каждый метод из `StudyRegistry.All()`** по каталогу задач
с известным решением и по реальной системе (DE441 / Horizons) в разных условиях.

Стенд отвечает на один вопрос владельца: **«какой метод лучший в каких условиях»**.

Два главных результата:

1. **Сертификат метода**: в каких задачах и режимах метод валиден (PASS), в каких не применим (N/A),

2. **Таблица рекомендаций**: для каждого режима (тега) и каждого уровня точности — какой метод
   дешевле всех среди прошедших, и с каким отрывом от второго.

## 8. Статусы и support matrix

Для каждой пары (метод, задача) и каждого уровня точности ровно один статус:

| статус | смысл |
|---|---|
| `PASS` | метод заявил поддержку, все применимые гейты пройдены, уровень достигнут в пределах бюджета |
| `FAIL` | метод заявил поддержку, но гейт нарушен или уровень не достигнут при доходе до самого мелкого control |
| `N/A` | `Supports(...)` вернул `false`; в CSV хранится `reason` из этого вызова. Это НЕ провал |
| `SKIP` | прогон оборван по бюджету (cap RHS/времени) или уровень не оценивается из-за oracle floor; причина обязательна |
| `ERROR` | исключение в стенде; требует разбора, в итоговом отчёте их должно быть 0 |

Правила:
1. `N/A` берётся **только** из `Supports(...)`. Руками прописывать N/A в раннере запрещено.
2. Если `Supports=true`, а метод физически не может задачу, это проявится как FAIL. Агент не «исправляет»
   `Supports` сам: записывает случай в `FOUND.md` и в «Вопросы к владельцу» в `PROGRESS.md`.
3. Должна быть автоматическая проверка согласованности флагов: для каждой задачи с силой, зависящей
   от скорости или массы (K8, R2, ship с drag/thrust, если есть), `ConservativeSecondOrder == false`, и все
   методы с расщеплением должны давать для неё `N/A`.

Ожидаемая картина (проверяется, а не навязывается): методы WH-* требуют центральное тело и консервативную силу;
Encke требует центральное тело; PEFRL / Y6 / Y6C / leapfrog / RKN12 / SRKN14A / GJ8 — консервативная `a(x)`;
DOP853 / DOPRI5 / RK4 — любая сила; IAS15 — в т.ч. зависящая от скорости. Реальный источник истины — `Supports(...)` в коде.

## 9. Гейты

Начальные значения порогов ниже предложены автором задания; владелец может поправить их **до начала M4**.
С начала M4 пороги заморожены (раздел 14, правило 4).

| гейт | что проверяется | правило |
|---|---|---|
| G1 точность | максимальная ошибка на checkpoint'ах против oracle | считается по уровням A1/A2/A3; находится наименьшая цена, при которой ошибка ≤ порога |
| G2 порядок | наблюдаемый порядок против `ExpectedOrder` (Richardson / наклон в log-log) | только fixed-step и только если `ExpectedOrder` не NaN. Наклон по ≥4 соседним точкам в области, где ошибка между 100×floor и 1e-2×масштаб. `\|p_obs − p_exp\| ≤ 0.5`. Если подходящих точек <4: «order: n/a (мало точек)», это не FAIL |
| G3 инварианты | дрейф энергии, момента импульса, центра масс | гейт только на консервативных задачах, где есть `EnergyFn` / `AngularMomentumFn`: `\|ΔE/E\| ≤ 10 × порог уровня`. На остальных только отчёт |
| G4 обратимость | вперёд-назад: возврат к начальному состоянию | **только информативно**, на PASS/FAIL не влияет (адаптивные методы не обязаны быть обратимы). Колонка `rev_err` |
| G5 конечность | нет NaN/Inf, нет `Abort` / `DomainViolation` | любое нарушение = FAIL |
| G6 детерминизм | два одинаковых прогона дают побитово одинаковое конечное состояние | однопоточно; нарушение = FAIL |
| G7 цена | вызовы RHS, шаги, отклонённые шаги, wall time, аллокации | отчёт. Превышение бюджета = SKIP, а не FAIL. Метрика цены для ранжирования — та, что принята в `REPORT_DATA_AUDIT.md` (single-price rule); дополнительно RHS calls и wall time |
| G8 аудит oracle | oracle сам корректен | см. ниже; выполняется **до** прогона методов |

**G8.** Для каждой задачи, пока oracle не прошёл аудит, задача помечается `INVALID` и методы по ней не оцениваются.
- Аналитические oracle: сверка с независимой формулой или с `KeplerUniversal`; остаток ≤ 1e-13 относительный.
- Certified reference: сходимость по 5 уровням шага (по существующему `CertifiedReference`) и, где доступно, совпадение со вторым независимым oracle (Taylor); результат записывается как «oracle floor» для задачи.
- Результат аудита в `results/<run>/oracle_audit.md`.

Измерения времени: wall time снимается **отдельным последовательным проходом** (прогрев, медиана ≥5 повторов,
как в уже существующем Retime Test562). Параллельный запуск (`--parallel`) допустим для ошибок и числа вызовов RHS,
но не для wall time.

## 11. Как определяется «лучший метод»

Для каждой пары (тег, уровень точности):
1. Берутся задачи с этим тегом, у которых уровень оценивается (oracle floor позволяет).
2. Если таких задач меньше двух, вывод: **«не доказано (менее 2 задач)»**. Рекомендация не выдаётся.
3. Кандидаты: методы, у которых на **всех** этих задачах статус PASS (N/A и FAIL исключают метод из кандидатов для этого тега).
4. Для кандидатов цена на каждой задаче нормируется на лучшую цену на этой задаче; итог = среднее геометрическое.
5. Метод с наименьшим итогом = «рекомендован». Если второй метод в пределах 15% по итогу, оба помечаются «ничья (в пределах шума цены)».
6. В таблице всегда пишутся: победитель, второй, отрыв, список методов, исключённых как N/A и как FAIL.

Порог 15% и правило «минимум 2 задачи» заморожены вместе с гейтами.

## 14. Правила работы (защита от ухода от задания)

1. **Источник истины** — этот файл и `PROGRESS.md`, а не память контекста.
2. Один этап за раз. Нельзя «заодно» сделать кусок следующего.
3. Любая идея вне задания → `BACKLOG.md`. Реализовывать её нельзя.
4. **Пороги, теги, уровни, правило раздела 11 не меняются после просмотра результатов.** Результат нельзя «подправить» изменением критерия.
   Если критерий оказался плохим, это «ЗАПРОС ИЗМЕНЕНИЯ ЗАДАНИЯ» к владельцу, а не самостоятельное решение.
5. Существующие тесты и результаты не изменяются (раздел 2). Новое пишется рядом.
6. Не угадывать. Если сведения (ИК, масса, формат файла) нельзя получить из репозитория или литературы, записать вопрос
   в «Вопросы к владельцу» и перейти к следующей независимой части.
7. Никакого хардкода результатов. Числа в отчётах только из CSV текущего прогона.
8. Каждый коммит относится ровно к одному этапу и содержит обновлённый `PROGRESS.md`.
9. Сообщать о фактах честно: что запущено и что нет, что прошло и что нет. «Должно работать» без запуска не считается результатом.
10. Если инструкции из чата противоречат этому файлу, агент не выполняет противоречащую часть молча, а ссылается на пункт TASK.md и спрашивает владельца.

## A1. Цель приложения

Старые тесты (Test552, 553, 554, 558, 559) отвечали на вопрос практики: **«сколько стоит достичь точности 100 / 10 / 1 м
в конкретном режиме полёта»**: у планеты, на высоких эксцентриситетах, на геостационарной высоте, в глубоком

## A7. Цели точности в метрах

Вид цели `M`: максимальная ошибка положения на checkpoint'ах (метрика из `ErrorBlocks` задачи) не больше N метров.

| цель | значение | на каких задачах |
|---|---|---|
| M100 | 100 м | все S, P, F, R1, R3, L1 |
| M10 | 10 м | то же |
| M1 | 1 м | то же |
| M0.1 | 0.1 м | S12, S15, L1, R3 и пролёты из F |
| M0.01 | 0.01 м | S12, S15, L1, R3 и пролёты из F |

Правила:
1. Цель оценивается только если floor эталона ≤ 0.1 × цель (правило G8 версии 1); иначе `SKIP` с причиной «oracle floor». Это заменяет старое правило «пропуск, если цель ниже 10×floor».
2. Статусы PASS/FAIL/N/A/SKIP/ERROR и гейты G1–G8 те же. Порог G3 для метровой цели: `10 × (цель / ScaleLength)`, на тех же задачах и с теми же исключениями («model drift»), что действуют в версии 1.
3. Уровни A1–A3 для задач K/T/R/L не меняются и не пересчитываются. На S, P, F уровни A1–A3 **не** вычисляются (колонки метровых целей заменяют их).
4. Цель в `matrix.csv` записывается в колонке `tier` строкой `M100`, `M10`, `M1`, `M0.1`, `M0.01`. Формат остальных колонок не меняется.
5. Новые цели не вводятся и значения не подбираются под результаты (правило 4 раздела 14).

## A8. Условия полёта: `conditions.csv`

В папке каждого прогона создаётся `conditions.csv`: одна строка на задачу. Все числа **вычисляются** по траектории эталона
или по параметрам builder'а, руками не вносятся (правило 7 раздела 14).

Колонки: `problem_id, class_tags, central_body, r_min_m, r_max_m, v_min_ms, v_max_ms, horizon_s, forces, velocity_dependent, oracle_id, oracle_floor_m, targets_evaluated`.

- `r_*` и `v_*`: экстремумы расстояния и скорости относительно центрального тела (если оно есть), иначе в системе задачи; в `central_body` указать, что именно.
- `forces`: список из `gravity, j2, drag, thrust, third-body, 1pn`.
- `targets_evaluated`: какие цели реально оценены (остальные SKIP по floor).

Это даёт связь «условие полёта → цена достижения цели»: скорость и расстояние теперь числа, а не пересказ.

## B1. Цель и главное правило

В репозитории уже есть отдельный стенд `Tools/P1bTests/Study/jpl/` (Test531–Test548): сравнение реальной системы с NASA/JPL Horizons DE441
и сравнение интеграторов на реальной силе. Приложение B переносит это в архитектуру Test564 в виде, где ничего не смешано.

Две разные задачи, два слоя:

| слой | вопрос | что фиксировано | что меняется | откуда |
|---|---|---|---|---|
| **V** (validation) | «модель воспроизводит NASA?» | эталонный интегратор | модель силы | Test537, 538, 544 |
| **I** (integrators) | «какой метод лучший на реальной силе?» | модель силы | метод | Test545, 546 (но против эталона той же модели) |

**Главное правило.** Ошибка относительно NASA **никогда не используется для ранжирования методов** и не входит в PASS/FAIL, рекомендации и цену.
Она в ней смешана с ошибкой модели (в `Study/jpl/README.md` это показано: RK4 на 1 сут «выигрывает» у DOP853 по Юпитеру из-за случайного
сокращения ошибок). Ошибка относительно NASA допустима только как справочная колонка с пометкой «смешивает ошибку модели и интегратора».

## B6. Цели для тира H

Цели M100, M10, M1 (A7) действуют по правилам A7. Для тира H добавляется второй вид цели **Q** («интегратор не портит модель»):

- `E_model` = ошибка модели этой задачи относительно Horizons на том же окне, из слоя V (`rms8_end`, и отдельно Луна).
- Для метода записывается `rms8_ref` и `moon_ref`: ошибка относительно эталона **той же модели**, посчитанная **той же функцией**, что `E_model`.
- Цель `Q10`: `rms8_ref ≤ 0.1 × E_model(rms8)` и `moon_ref ≤ 0.1 × E_model(Moon)`. Цель `Q1`: то же с коэффициентом 0.01.
- Цель оценивается только если floor эталона не больше 0.1 × (цель, пересчитанная в метры). Иначе SKIP «oracle floor».

Смысл: `Q10` отвечает на вопрос «при какой цене метод добавляет не более 10 % к ошибке модели».
Для сведения (не порог): в README `Study/jpl` ошибка Newton-модели 2026 около 739 км, 1PN около 7.4 км, full409 около 1.1 км.

Справочная колонка (не для ранжирования): `err_vs_horizons_rms8` на сертифицирующем control, подпись «смешивает ошибку модели и интегратора».

# ПРИЛОЖЕНИЕ C (версия 4): перенос интеграторов в игру, поэтапно и с проверкой

Приложение C дополняет разделы 1–15 и Приложения A, A-fix, B. Этапы M0–M7, S0–S7 и B0–B6 выполнены.
Эталон регрессии стенда: `baseline/20261114T093336Z_f899097` (или более новый из `BASELINE.md`).

**Приложение C отменяет запрет «не портируем метод в игру» (§2 версии 1 и B2) только в границах этого приложения,
и только на перечисленных ниже условиях.** Вне этих границ запрет действует.

## C1. Цель и главное правило

Перенести в игру те интеграторы, которые стенд показал лучшими, **без потери надёжности** текущего пути
(DOP853 по умолчанию, DOPRI5 как опция) и **без изменения поведения игры, пока флаги выключены**.

Таблица стенда это карта гипотез, а не разрешение включать. Причины (проверены по коду, `Assets/_Project/Scripts/...`):
1. Игра режет шаг до `OrbitIntegrator.DefaultMaxStepSize = 600 с`; стенд считал без этого лимита, и победители стенда используют шаги в тысячи секунд. Рейтинг на 600 с может измениться (GEO, LEO).
2. Игра считает кораблём в чанках; в живом режиме шаг привязан к кадру, там число стадий метода важнее допуска (DOP853 дешевле на цену стадий, чем RKN12).
3. Игровой путь использует dense output (`DenseSegment`) для событий (`EventDrivenPropagator`); у study-методов его нет.
4. Игровой DOPRI5/DOP853 (`SpacecraftOrbitIntegrator`) в прогон стенда не входил; сравнивать надо с ним.
5. Планеты в игре идут по кеплеровым рельсам и запечённым эфемеридам; N-body интегрируется только корабль. Результаты стенда по планетам (R1, R2, P*, H*, T*) для игры не применимы.

Поэтому порядок такой: **сначала измерить в условиях игры, потом решить, что переносить, потом переносить по одному.**

## C3. Кандидаты и исключения

Кандидаты на порт (по результатам стенда, `WHICH_INTEGRATOR_WHEN.md`), в порядке приоритета:
1. **RKN12(10)**: лучший для консервативной гравитации; адаптивный; не требует истории и центрального тела. Работает только без массового расхода и тяги/сопротивления (ограничение `Rkn1210Stepper` в стенде), то есть только при `CanCoast == true`.
2. **WH-BM14A / WH-Y6**: почти круговые орбиты у планеты (LEO/GEO), только долгий coast, фиксированный шаг, центральное тело. Порт условный (C7).
3. **IAS15**: хаос и тесные сближения. Порт условный и только если в игре есть такой геймплей (решение владельца).

Не переносятся (нет побед или ненадёжный сертификат): RK4, Leapfrog, PEFRL, Y6, Y6C, DOPRI5-fixed, SRKN14A, GJ8, Encke-IAS15.

## C7. Порт одного метода (шаблон для каждого кандидата)

Метод портируется отдельным этапом и отдельной веткой. Для **RKN12(10)** (первый кандидат), а для WH и IAS15 по тому же шаблону после отдельного решения владельца:

Новое значение в `SpacecraftIntegrator` (добавляется в конец перечисления, значения существующих не меняются).

3. **События и dense output.** Игра ищет события по `DenseSegment`. Для метода выбирается и обосновывается измерением одна из стратегий: (а) пересчёт подинтервала от начала принятого шага до нужного момента; (б) интерполяция Эрмита с документированной оценкой ошибки не больше 0.1 допуска. 4. **Кадры.** Оба пути `SpacecraftPhysics` (локальный кадр и абсолютный) покрыты.
5. **Тесты.** Паритет: тот же сценарий, что в игре, с флагом и без; при выключенном флаге результат побитово прежний; при включённом: ошибка против certified reference не больше `Prod-DOP853` × 1.5, время события отличается от пути DOP853 не более чем на 1 мс, результат детерминирован (два прогона побитово равны), аллокации в горячем пути не больше, чем у DOP853.
