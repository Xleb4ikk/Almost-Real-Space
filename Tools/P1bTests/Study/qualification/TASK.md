## 1. Цель

Построить **изолированный стенд квалификации методов интегрирования**: консольный прогон без Unity
и без `StarSystem`, который прогоняет **каждый метод из `StudyRegistry.All()`** по каталогу задач
с известным решением и по реальной системе (DE441 / Horizons) в разных условиях.

Стенд отвечает на один вопрос владельца: **«какой метод лучший в каких условиях»**.

Два главных результата:

1. **Сертификат метода**: в каких задачах и режимах метод валиден (PASS), в каких не применим (N/A),
   в каких заявил поддержку, но не прошёл (FAIL); точность, наблюдаемый порядок, дрейф инвариантов, цена.
2. **Таблица рекомендаций**: для каждого режима (тега) и каждого уровня точности — какой метод
   дешевле всех среди прошедших, и с каким отрывом от второго.

Это замена «каши» из Test549–Test563: единый каталог, единые гейты, единый отчёт.

## 8. Статусы и support matrix

Для каждой пары (метод, задача) и каждого уровня точности ровно один статус:

| статус | смысл |
|---|---|
| `PASS` | метод заявил поддержку, все применимые гейты пройдены, уровень достигнут в пределах бюджета |
| `FAIL` | метод заявил поддержку, но гейт нарушен или уровень не достигнут при доходе до самого мелкого control |
| `N/A` | `Supports(...)` вернул `false`; в CSV хранится `reason` из этого вызова. Это НЕ провал |
| `SKIP` | прогон оборван по бюджету (cap RHS/времени) или уровень не оценивается из-за oracle floor; причина обязательна |
| `ERROR` | исключение в стенде; требует разбора, в итоговом отчёте их должно быть 0 |

Правила:
1. `N/A` берётся **только** из `Supports(...)`. Руками прописывать N/A в раннере запрещено.
2. Если `Supports=true`, а метод физически не может задачу, это проявится как FAIL. Агент не «исправляет»
   `Supports` сам: записывает случай в `FOUND.md` и в «Вопросы к владельцу» в `PROGRESS.md`.
3. Должна быть автоматическая проверка согласованности флагов: для каждой задачи с силой, зависящей
   от скорости или массы (K8, R2, ship с drag/thrust, если есть), `ConservativeSecondOrder == false`, и все
   методы с расщеплением должны давать для неё `N/A`.

Ожидаемая картина (проверяется, а не навязывается): методы WH-* требуют центральное тело и консервативную силу;
Encke требует центральное тело; PEFRL / Y6 / Y6C / leapfrog / RKN12 / SRKN14A / GJ8 — консервативная `a(x)`;
DOP853 / DOPRI5 / RK4 — любая сила; IAS15 — в т.ч. зависящая от скорости. Реальный источник истины — `Supports(...)` в коде.

## 9. Гейты

Начальные значения порогов ниже предложены автором задания; владелец может поправить их **до начала M4**.
С начала M4 пороги заморожены (раздел 14, правило 4).

| гейт | что проверяется | правило |
|---|---|---|
| G1 точность | максимальная ошибка на checkpoint'ах против oracle | считается по уровням A1/A2/A3; находится наименьшая цена, при которой ошибка ≤ порога |
| G2 порядок | наблюдаемый порядок против `ExpectedOrder` (Richardson / наклон в log-log) | только fixed-step и только если `ExpectedOrder` не NaN. Наклон по ≥4 соседним точкам в области, где ошибка между 100×floor и 1e-2×масштаб. `\|p_obs − p_exp\| ≤ 0.5`. Если подходящих точек <4: «order: n/a (мало точек)», это не FAIL |
| G3 инварианты | дрейф энергии, момента импульса, центра масс | гейт только на консервативных задачах, где есть `EnergyFn` / `AngularMomentumFn`: `\|ΔE/E\| ≤ 10 × порог уровня`. На остальных только отчёт |
| G4 обратимость | вперёд-назад: возврат к начальному состоянию | **только информативно**, на PASS/FAIL не влияет (адаптивные методы не обязаны быть обратимы). Колонка `rev_err` |
| G5 конечность | нет NaN/Inf, нет `Abort` / `DomainViolation` | любое нарушение = FAIL |
| G6 детерминизм | два одинаковых прогона дают побитово одинаковое конечное состояние | однопоточно; нарушение = FAIL |
| G7 цена | вызовы RHS, шаги, отклонённые шаги, wall time, аллокации | отчёт. Превышение бюджета = SKIP, а не FAIL. Метрика цены для ранжирования — та, что принята в `REPORT_DATA_AUDIT.md` (single-price rule); дополнительно RHS calls и wall time |
| G8 аудит oracle | oracle сам корректен | см. ниже; выполняется **до** прогона методов |

**G8.** Для каждой задачи, пока oracle не прошёл аудит, задача помечается `INVALID` и методы по ней не оцениваются.
- Аналитические oracle: сверка с независимой формулой или с `KeplerUniversal`; остаток ≤ 1e-13 относительный.
- Certified reference: сходимость по 5 уровням шага (по существующему `CertifiedReference`) и, где доступно, совпадение со вторым независимым oracle (Taylor); результат записывается как «oracle floor» для задачи.
- Результат аудита в `results/<run>/oracle_audit.md`.

Измерения времени: wall time снимается **отдельным последовательным проходом** (прогрев, медиана ≥5 повторов,
как в уже существующем Retime Test562). Параллельный запуск (`--parallel`) допустим для ошибок и числа вызовов RHS,
но не для wall time.

## 11. Как определяется «лучший метод»

Для каждой пары (тег, уровень точности):
1. Берутся задачи с этим тегом, у которых уровень оценивается (oracle floor позволяет).
2. Если таких задач меньше двух, вывод: **«не доказано (менее 2 задач)»**. Рекомендация не выдаётся.
3. Кандидаты: методы, у которых на **всех** этих задачах статус PASS (N/A и FAIL исключают метод из кандидатов для этого тега).
4. Для кандидатов цена на каждой задаче нормируется на лучшую цену на этой задаче; итог = среднее геометрическое.
5. Метод с наименьшим итогом = «рекомендован». Если второй метод в пределах 15% по итогу, оба помечаются «ничья (в пределах шума цены)».
6. В таблице всегда пишутся: победитель, второй, отрыв, список методов, исключённых как N/A и как FAIL.

Порог 15% и правило «минимум 2 задачи» заморожены вместе с гейтами.

## 14. Правила работы (защита от ухода от задания)

1. **Источник истины** — этот файл и `PROGRESS.md`, а не память контекста.
2. Один этап за раз. Нельзя «заодно» сделать кусок следующего.
3. Любая идея вне задания → `BACKLOG.md`. Реализовывать её нельзя.
4. **Пороги, теги, уровни, правило раздела 11 не меняются после просмотра результатов.** Результат нельзя «подправить» изменением критерия.
   Если критерий оказался плохим, это «ЗАПРОС ИЗМЕНЕНИЯ ЗАДАНИЯ» к владельцу, а не самостоятельное решение.
5. Существующие тесты и результаты не изменяются (раздел 2). Новое пишется рядом.
6. Не угадывать. Если сведения (ИК, масса, формат файла) нельзя получить из репозитория или литературы, записать вопрос
   в «Вопросы к владельцу» и перейти к следующей независимой части.
7. Никакого хардкода результатов. Числа в отчётах только из CSV текущего прогона.
8. Каждый коммит относится ровно к одному этапу и содержит обновлённый `PROGRESS.md`.
9. Сообщать о фактах честно: что запущено и что нет, что прошло и что нет. «Должно работать» без запуска не считается результатом.
10. Если инструкции из чата противоречат этому файлу, агент не выполняет противоречащую часть молча, а ссылается на пункт TASK.md и спрашивает владельца.
