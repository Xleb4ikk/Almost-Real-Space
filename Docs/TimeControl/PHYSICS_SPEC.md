# PHYSICS_SPEC — перемотка и ускорение времени

Скоуп: `TimeControlModel` / `TimeControlRuntime` / точки перемотки, `WarpController`,
`WarpPlanner`, `LongWarpDriver`, `DetectionGrain`. Законы движения корабля не меняются —
меняется только то, **сколько модельного времени проживается за кадр** и **как
восстанавливается прошлое состояние**.

## 1. Символы, единицы, кадры

| Символ | Смысл | Единица | Где живёт |
|---|---|---|---|
| `t` | модельное время (TDB-подобное, от эпохи сцены) | s | `VesselStep.TimeSeconds`, двойная точность |
| `T_launch` | время включения физики (точка 0) | s | `TimeControlRuntime.launchTimeSeconds` |
| `t_flight` | `t − T_launch` — число на точке и в таймере | s | `TimeControlModel.CurrentFlightSeconds` |
| `t_real` | РЕАЛЬНЫЕ секунды полёта (по ним сетка точек) | s | Kahan-аккумулятор таймлайна |
| `k` | номер точки = номер реальной минуты | — | `FlightCheckpoint.Index` |
| `r, v` | абсолютные положение/скорость в инерциальной системе | m, m/s | `Spacecraft`, `Vector3d` |
| `μ` | гравитационный параметр тела | m³/s² | `OrbitingBody.ResolveStandardGravitationalParameter()` |
| `h` | шаг интегрирования | s | внутри `SpacecraftOrbitIntegrator` |

Рендер (`float32`, `Transform`) в физику не входит: всё считается в `double` и
переводится в рендер только через `FloatingOrigin.ToRender`.

## 2. Управляющие уравнения

Движение аппарата — та же система, что и до задачи (ньютоновская N-тельная задача):

- `r̈ = Σ_i μ_i (r_i − r) / |r_i − r|³ + a_неграв(r, v, t)`
- негравитационные источники: `ThrustSource` / `StageThrustSource`, `DragSource`,
  `FlightThrustSource`; проверяются формально (`LongWarpDriver.CanEnterLongWarp`).

Формулы, использованные в проверках (ID из `references/formulas/` навыка):

| ID | Что | Применение |
|---|---|---|
| F-FUND-04 | виз-вива `v² = μ(2/r − 1/a)` | скорость удара при радиальном падении (`a = r0/2`) |
| F-KEP-10 | радиальное падение `r = (r0/2)(1+cos η)`, `t = √(r0³/(8μ))(η+sin η)` | время касания на ×1 000 000 |
| F-KEP-01 | уравнение Кеплера (эллипс) | контроль орбитальных элементов |
| F-FUND-09 | третий закон Кеплера `T = 2π√(a³/μ)` | период в R3 |

## 3. Два режима ускорения и что с ними происходит физически

### 3.1 Physical ×1…×6 (тяга разрешена)

- Шаг модели **не огрубляется**: тик управления `0.5 с` модельного времени, чанк
  полётной модели `0.05 с` модельного времени (`VesselStep.FlightChunkSeconds`).
- При ×6 в кадр укладывается в 6 раз больше чанков; допуски DOP853
  (`1e-6 м`, `1e-9` относительной) не меняются.
- Измерено (R1, 600 с полёта): расхождение «×6 против ×1» 2.5e-4…1.1e-3 м, при
  собственной зависимости модели от частоты кадров 5.1e-4 м. То есть варп не добавляет
  своего класса ошибки.
- Измерено (R10, 12 с тяги): Δv на ×4 и ×6 **бит-в-бит** равно ×1 (`dvVsX1 = 0`,
  `dMassVsX1 = 0`), а само Δv сходится с Циолковским до 0.05 %.
- В атмосфере и на посадке эффективный фактор капается ×3 (`AtmosphereMaxWarpFactor`) —
  это сохранённое ограничение, а не следствие новой логики.

### 3.2 Full ×10…×1 000 000 (только баллистика)

- Тяга принудительно ноль. Вход — только при формальном `CanEnterLongWarp`
  (вклад всех негравитационных источников ровно нулевой); иначе кадр идёт физической
  цепочкой с капом ×3 и одним предупреждением в лог.
- Интегратор адаптивный, точность задаётся допусками, а не размером окна: на ×1 000 000
  в дальнем космосе это ~27 чанков по 600 с на кадр, у планеты зерно событий дробится
  (`DetectionGrain`) до `MaxChunkSeconds / MaxSubdivisions = 3 с`.
- Бюджет кадра: `LongWarpDriver.FrameBudgetMilliseconds = 6` мс; недоигранное переносится,
  часы показывают прожитое время (недобор темпа — объявленное отклонение).
- Горизонт: `WarpPlanner` клампит к `BakedEndSeconds − t`; после него кадр не летит.

### 3.3 Анти-туннель (важное)

На ×1 000 000 одно «окно» кадра — 16 000 модельных секунд, поэтому событие поверхности
обязано искаться внутри, а не по концам кадра. Это делает `DetectionGrain`:
`NeedsFineGrain` решает, может ли аппарат дойти до сферы за чанк, и дробит чанк.

**Исправлено по ходу задачи** (найдено R2): прежняя оценка достижимости
`(|v_корабля| + |v_тела|)·chunk·2` не учитывала ускорение и брала СУММУ модулей вместо
относительной скорости. Падение «с нуля относительной скорости» (сброс с высоты) при
этом считалось недостижимым: чанк 600 с проскакивал тело насквозь, аппарат вылетал
со скоростью 1.7e14 м/с. Теперь:

```
reachable = (|v_отн|·τ + ½·|a(r)|·τ²)·2 ,  τ = chunk
```

и `a(r)` берётся из самой модели (`EvaluateShipAcceleration`). R2 после исправления:

| Величина | Измерено | Аналитика (μ модели) | Δ | Допуск |
|---|---|---|---|---|
| время касания | 88.7914 s | 88.7911 s | 2.7e-4 s | 1.9e-3 s |
| скорость удара | 2253.859 m/s | 2253.837 m/s | 2.3e-2 m/s | 5.3e-2 m/s |
| `r_event − R` | −1.85e-3 m | 0 | — | ±1 m |

## 4. Перемотка — восстановление состояния, не обратная интеграция

Тела и эфемериды — чистые функции времени, поэтому «прошлое» задаётся парой
(время, состояние аппарата). Откат = восстановление снимка; ошибки интегрирования
не накапливаются, обратимость точная.

### 4.1 Что входит в снимок

| Компонент | Поле |
|---|---|
| часы | `t` |
| аппарат | `r, v, m, ориентация, ω, PositionIsCom`, режим, доминирующее тело, детали |
| топливо | `firstAttached, ignited, DetachedMassKg, Revision, AutoIgnite`, все пулы |
| SAS | `holdValid`, `holdTarget` |
| исполнительные органы | уровни тяги, углы подвеса, остаток РСУ |
| обломки | активные слоты с индексами, `nextSequence` |
| игрок | поза, скорость, режим, кресло, EVA, ground source |
| локальные кадры | инвалидируются (`Spacecraft.InvalidateLocalState`) |

Тумблеры двигателей и РСУ — намерение игрока, не откатываются (объявлено).

### 4.2 Межкадровые хвосты — решения

| Хвост | Решение |
|---|---|
| Kahan-аккумулятор `time` в `VesselStep` | `ResetTimeAccumulator()` при восстановлении |
| фаза тика управления 0.5 с | `Warp.ResetTicks(t)` |
| остаток чанка полётной модели | между кадрами не хранится (считается от текущего `t`) |
| бюджет долгого варпа | локальный `Stopwatch` в вызове — переносить нечего; `CancelRequested` сбрасывается |
| `DenseSegment` рендера | между кадрами не хранится |
| `EphemerisRuntime`/`WarpPlanner` | чистые функции входа |
| кеш `DebrisUpdater` | инвалидируется по несовпадению времени |
| варп | **не восстанавливается**: после любой перемотки Physical ×1 |

### 4.3 Две шкалы

- `t_real` — Kahan-сумма `Time.deltaTime` тех кадров, где модельное время реально
  изменилось. `t += dt` запрещён: систематический дрейф (см. `references/time-and-phase.md`).
- `t_flight = t − T_launch` — число на точке и в главном таймере; при варпе не равно `60·k`.

Точка `k` снимается при пересечении `t_real = 60·k`. После отката на `k`
`t_real` берётся из снимка, `nextIndex = k+1`, точка `k` заново не пишется. Точки не
удаляются; будущие остаются выбираемыми и перезаписываются по мере продвижения.

## 5. Инварианты

1. `t` монотонно растёт внутри одной ветви; откат — единственный разрыв.
2. `t_flight` в точках может быть немонотонным — таймеры показывают точное значение.
3. Индексы точек непрерывны от 0; дублей и пропусков нет.
4. Точка 0 не перезаписывается (исключение — новый полёт через `ResetForLaunch`).
5. После отката варп строго Physical ×1.
6. В контактной зоне (PhysX) точки серые, откат запрещён; точка 0 восстанавливается
   через билдер (зона и прокси создаются заново).

## 6. Бюджет ошибки

| Источник | Оценка | Где измерено |
|---|---|---|
| интегрирование, 600 с полёта ×1 | 5.1e-4 м (собственная чувствительность к fps) | R1 |
| варп ×6, те же 600 с | 2.5e-4…1.1e-3 м | R1 |
| восстановление снимка (без тяги) | 0 м, 0 м/с, 0 кг (бит-в-бит) | R4 |
| восстановление снимка (с тягой 60 с) | 0 м, 0 м/с, 0 кг, пулы 0 кг | R4b |
| событие поверхности на ×1e6 | 2.7e-4 с, 2.3e-2 м/с | R2 |
| часы `t_real`, 1e5 рваных кадров | ≤ 8 ulp точной суммы | xunit R5 |

## 7. Отклонения

1. Перемотка = восстановление снимка, не обратная интеграция.
2. В контактной зоне откат запрещён (кроме точки 0 через билдер), точки серые.
3. Выше ×6 модель меняется: баллистика без тяги и сопротивления (проверяется формально).
4. Атмосфера/посадка: эффективный фактор ≤ ×3.
5. Темп на ×10⁵…×10⁶ у планеты ограничен бюджетом кадра.
6. Тумблеры двигателей/РСУ не откатываются, цель SAS откатывается.
7. Сетка точек по реальному времени, в модельном — неравномерна.
8. Лимит хранимых состояний 4096; при переполнении освобождаются самые старые по
   индексу (кроме точки 0), точка остаётся серой.

## 8. Найденные по ходу задачи дефекты (не этой задачи, но исправлены/зафиксированы)

1. **Порядок `GetMaxChunkSeconds` / `SampleControl`**: граница тика сдвигалась до
   выборки снимка, из-за чего `ControlInputSnapshot.Throttle` переставал обновляться
   навсегда (газ замирал на первом снимке). Исправлено: `SampleControl` первым,
   границу двигает только он. Проверено R4b/R10.
2. **`DetectionGrain.ReachableDistance`**: см. §3.3. Исправлено, проверено R2.
3. **`μ` тела расходится с полем**: `ResolveStandardGravitationalParameter()` для
   Aeolus = 7.60121e16, а поле, которое реально считает `CachedGravitySource`,
   соответствует 7.7683e16 (отношение 1.02199). Не исправлялось (данные сцены,
   не код этой задачи); зафиксировано в отчёте — двухтельная аналитика обязана
   брать μ из модели.
4. **Точность пропагатора на высокоэксцентричной орбите**: дрейф `a` ~1.4 % за 2 периода
   воспроизводится и на физической цепочке ×1 (R3slow), то есть к варпу отношения не
   имеет. См. VERIFICATION_REPORT R3.
