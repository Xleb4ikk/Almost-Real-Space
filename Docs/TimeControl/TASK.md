# ЗАДАЧА-КОНТРАКТ: панель времени (перемотка + ускорение)

Статус: **канон**. Всё, что сделано иначе, обязано быть записано в
`Docs/TimeControl/VERIFICATION_REPORT.md`, раздел «Отклонения», с причиной и числом.
Молчаливое отклонение = баг.

Проект: Unity 6000.6.0f1, HDRP, real-scale. Абсолютные позиции — `Galilego.Core.Vector3d`,
рендер — через `Galilego.Universe.FloatingOrigin.ToRender`.

---

## 0. Границы задачи

**Делаем:** подключение готовой панели к симуляции, перемотка по реальным минутам,
два режима ускорения времени, точное восстановление состояния, верификация числами.

**Не делаем:** редизайн панели. `TimeControlPanel` / `TimeControlModel` меняются только
в объёме раздела 11. Ничего из существующего поведения варпа не выбрасывается: старый
`SetWarpFactor(double)` и клавиши 1…7 (`ShipController`, `CheatMenu`,
`SpacecraftBuilder`) продолжают работать.

**Обязательные навыки** (не один): `astrophysics-game-physics` (формулы по ID из
`references/formulas/`, гейты 0–5, спека, отчёт), `using-unity` → `unity-pipeline`
(живая сцена, компиляция, Play Mode, скриншоты), `ui-imgui` (правки IMGUI-панели).

---

## 1. Решения заказчика (окончательные, не обсуждаются)

1. **Физическое ускорение ×1, ×2, ×3, ×4, ×6** — тяга РАЗРЕШЕНА, физика прежняя:
   шаг модели не огрубляется. **Полное ускорение ×10…×1 000 000** — тяга запрещена,
   чистая баллистика.
2. **Точка 0** — момент, когда игрок запустил физику (`SpacecraftBuilder.EnterFlightAt`),
   именно этот кадр и это время.
3. **При любой перемотке варп ВСЕГДА сбрасывается в физический ×1.** Варп из снимка
   не восстанавливается никогда.

---

## 2. Поведение (что получает игрок)

- Точка создаётся каждую **реальную** минуту полёта. Точка `k` — когда реальные секунды
  полёта пересекают `60·k`; `k = 0` — старт.
- Перемотка на любую доступную точку. Старые точки **не удаляются**.
- После перемотки на `k` следующие минуты пишутся **поверх** старых (`k+1`, `k+2`, …);
  когда playhead догнал прежний конец — линия с `k` переписана полностью.
- Точки «будущего», ещё не перезаписанные, остаются выбираемыми; перемотка вперёд
  на них разрешена.
- Над линией — время полёта «сейчас» (модельные секунды от старта). Под линией —
  модельное время ВЫБРАННОЙ точки от старта (при варпе ≠ `60·k`). После подтверждения
  перемотки основной таймер равен времени выбранной точки.
- Ускорение: слот ×1 с выездом ×2/×3/×4/×6 слева; ряд ×10…×1 000 000 справа.

---

## 3. Две шкалы времени — не смешивать

| Имя | Что | Где живёт |
|---|---|---|
| `RealSeconds` | реальные секунды полёта; по ним сетка точек | Kahan-аккумулятор, **не** `t += dt` |
| `FlightSeconds` | `Runner.TimeSeconds − launchTime` | модели, на точке, нижний таймер |

- `RealSeconds` начисляется на `Time.deltaTime` тех кадров, в которых симуляция реально
  шла (модельное время изменилось).
- В точке сохраняются ОБА значения. `RealSeconds` — фактическое на момент снятия,
  **не** округлённое `60·k`.
- При откате `RealSeconds` берётся из снимка точки.
- Время полёта в точках может быть **немонотонным** (после перемотки вперёд на
  «устаревшую» точку). Таймеры показывают точное время выбранной точки, без допущений
  о порядке.

## 4. Таймлайн

### 4.1 `Core/Simulation/FlightCheckpointTimeline.cs` (новый, без Unity)

Чистый C#, компилируется в `Tests/GalilegoPhysicsTests` (глоб `Core/**`).
Kahan-часы; `Advance(realDt)`; `Capture(index)`; `Rewind(index)`; перезапись при
существующем индексе; выбор точки; лимит памяти.

**Модель точки:**
```csharp
enum PointKind { Launch, Flight, Blocked }
sealed class Point<T> { double RealSeconds; double FlightSeconds; PointKind Kind; T State; }
```
`PointCount` = число записанных точек, включая «будущие» = `Model.PointFlightSeconds.Count`.
Индексы всегда непрерывны от 0 (см. 4.2: пропуски в зоне не допускаются).

**Правила продвижения:**
- НЕ продвигать при: пауза, билд-режим, симуляция не шла в кадре, корабль разрушен.
- Откат при разрушенном корабле **разрешён** — это основной сценарий спасения.
- Пересечение нескольких минут за кадр → записать каждую, без пропусков и дублей.
- Перезапись: точка с индексом есть → заменить; нет → добавить.
- Откат на `k`: восстановить снимок, `RealSeconds` из снимка, `nextIndex = k+1`,
  точку `k` заново не писать.
- Откат на текущую позицию playhead: панель уже отдаёт `-1`, кнопка неактивна.
- Лимит памяти: `MaxPoints` (по умолчанию 4096 ≈ 68 часов полёта). При переполнении —
  не молчаливая потеря: сохраняются точка 0 и последние `MaxPoints-1`, между ними
  дыра; попытка выбрать дыру отклоняется с `Notice`. Политика фиксируется в спеке.
  (Индексы при этом НЕ перенумеровываются: `PointIndex` — абсолютный номер минуты.)

### 4.2 Точка 0 и контактная зона

Площадка = контактная зона (`ContactZoneHost.Active`), PhysX невосстановим.

- Точка 0 снимается в `EnterFlightAt` в момент передачи физике, `Kind = Launch`.
- Откат на точку 0 идёт **не** через `RestoreWorldSnapshot`, а через путь
  «вернуться в билдер → `EnterFlightAt`»: `ReturnToBuild()` (восстанавливает
  `launchSnapshot`: время, корабль, игрок; чистит обломки и ступени; выводит из зоны),
  затем `SetPhysics(true)` → `EnterFlightAt(t)` на следующем кадре, зона и PhysX-прокси
  создаются заново. Время — восстановленное.
- При повторном входе `EnterFlightAt` НЕ обнуляет таймлайн (флаг
  `reenteringFromRewind`), иначе перемотка уничтожит саму себя.
- Если билдера нет (чит-спавн на орбите) — точка 0 имеет `Kind = Flight` и
  восстанавливается обычным снимком.
- Пока `ContactZoneHost.Active`, `RealSeconds` идут (минуты не теряются), точки
  создаются как `Kind = Blocked` (серые, откат запрещён) — индексы не съезжают.
  Как только корабль вышел из зоны — точки пишутся нормально.
- Откат на `Blocked` отклоняется с `Notice` в панели.
- Перезапись/повреждение точки 0 — ошибка; покрыть тестом.

### 4.3 Полный состав снимка обычной точки

Обязано восстанавливаться:

| Что | Как |
|---|---|
| время, корабль (поз/скорость/масса/ориентация/ω/`PositionIsCom`), режим, доминирующее тело, детали | существующий `WorldSnapshot` |
| игрок (поза, скорость, режим, кресло, EVA, ground source) | существующий `WorldSnapshot` |
| `StagePropulsion` | новый `CaptureState/RestoreState`: `firstAttached`, `ignited`, `DetachedMassKg`, `Revision`, `AutoIgnite`, все `StagePoolState` |
| `VesselFlightModel` SAS | новый `CaptureHoldState/RestoreHoldState`: `holdValid`, `holdTarget` |
| `DebrisPool` | компактный снимок активных слотов; при откате `Clear` + вставка на те же индексы |
| локальный кадр `Spacecraft` | новый `InvalidateLocalState()`; вызывать для корабля и всех активных обломков |

**Все зафиксированные переключатели (SAS, РСУ, включённость двигателей) и газ откатываются. Физическое удержание клавиш — живой ввод, не восстанавливается.**

### 4.4 Межкадровые «хвосты» — по каждому пункту явное решение

| Хвост | Решение |
|---|---|
| Kahan `time` в `VesselStep` | `SetTime`/`ResetTimeAccumulator` при откате (сброс) |
| фаза тика управления 0.5 с | `Warp.ResetTicks(t)` при откате |
| остаток чанка полётной модели 0.05 с | не хранится между кадрами (`StepFlying` считает от текущего t) — проверить и записать |
| недоделанный бюджет варпа | обнулить (перенос на следующий кадр отменяется) |
| `DenseSegment` рендера | не хранится между кадрами — проверить и записать |
| `EphemerisRuntime`/`WarpPlanner` | чистые функции входа — проверить и записать |
| `DebrisUpdater` кеш тел | сбрасывается по несовпадению времени — проверить и записать |
| варп | **не восстанавливать**, принудительно Physical ×1, `PhysicalFactor=1`, `ActiveKind=Physical`, сброс планировщика и бюджета |

### 4.5 Момент применения отката

`RewindRequested` приходит из IMGUI (`OnGUI`), мир там менять нельзя.
- запрос ставится в очередь;
- применяется в начале `Update` раннера, ДО `StepFlying/StepLanded`, чтобы шаг в том же
  кадре не затёр восстановленное;
- один запрос на кадр, остальные отбрасываются.

## 5. Варп

### 5.1 `WarpController`

```csharp
enum WarpMode { Physical, Full }
PhysicalRungs = {1,2,3,4,6}
FullRungs     = {10,50,100,500,1000,10000,100000,1000000}
SetPhysicalWarp(int) / SetFullWarp(double)
EffectiveThrottle(...) => Mode == Full ? 0 : rawThrottle
```
- Тяга разрешена в `Physical` до ×6 включительно (`ThrustMaxWarpFactor` больше не
  режет ×4/×6).
- Кап ×3 в атмосфере/посадке (`AtmosphereMaxWarpFactor`) сохраняется.
- Старый `SetWarpFactor(double)` — обёртка по объединённой таблице; ни одна ступень не
  теряется (включая 3000).

### 5.2 `WarpPlanner` / `EphemerisRuntime`

- Решение «долгий варп» только при `LongWarpDriver.CanEnterLongWarp == true`.
- Иначе — физическая цепочка с капом ×3 + одноразовый лог.
- Сейчас guard в долгом пути не вызывается — это дыра, закрыть.

### 5.3 `LongWarpDriver`

- Срезы по `MaxChunkSeconds` + бюджет по `Stopwatch`; недоигранное переносится на
  следующий кадр.
- Горизонт `BakedEndSeconds`: часы встают ровно, без перелёта.

### 5.4 Инвариант `StepPlayer`

При ×6 и `Time.deltaTime` до 0.333 с кадр = до 2 модельных секунд. Кап `playerCap = 4`
больше не соответствует верхнему физическому фактору. Перепроверить: игрок в кабине /
сидит / EVA не должен «теряться». Решение (увеличить подшаги либо ограничить фактор по
`realDt`) обосновать и записать. Слот панели показывает РЕАЛЬНО применённый фактор,
никакого молчаливого среза.

### 5.5 Требование к шагу

При ×4/×6 шаг модели НЕ меняется: тик управления 0.5 с, чанк полётной модели 0.05 с
модельного времени. Подтвердить **измерением** (число внутренних шагов DOP853 на
модельную секунду), не словами.

## 9. Верификация — критерии фиксированы ДО прогона

| # | Проверка | Критерий |
|---|---|---|
| R1 | ×1 vs ×6 при 30 и 60 fps, LEO, 3600 с | разница на уровне допуска интегратора DOP853 (`1e-6 м` / `1e-9`); сравнить с базой «×1 vs ×1 при разных fps», а не с нулём |
| R2 | Радиальное падение с 100 км на ×1M, тело БЕЗ атмосферы | время касания ≤1e-3 с и скорость удара ≤1e-2 м/с от аналитики (формула по ID из `references/formulas/`) |
| R2b | То же над телом с атмосферой | долгий варп запрещён guard-ом, работает физическая цепочка ×3, лог |
| R3 | Орбита e≈0.9, ×1M, N периодов | перигей в допуске, ни одного прохода под поверхностью |
| R4 | Снимок → 60 с → снимок → откат → те же 60 с с теми же входами | совпадение в пределах допуска интегратора на чистом степпере с фиксированным dt (ловит забытое состояние) |
| R5 | 1e5 кадров с рваным dt | `RealSeconds` vs точная сумма ≤ нескольких ulp; индексы ровно `floor(t/60)`, без пропусков и дублей |
| R6 | ×1M у конца эфемериды | часы ровно на горизонте |
| R7 | Откат на точку 0 из свободного полёта | состояние = состояние в `EnterFlightAt` (топливо, ступени, масса, поза, время, игрок), зона активна, варп ×1 |
| R8 | Откат при любом варпе (×6, ×1M, перенос бюджета) | после отката Physical ×1, остатки планировщика/бюджета обнулены |
| R9 | Откат из разрушенного корабля | обломки «из будущего» исчезли, корабль цел, точки не перезаписаны посмертным состоянием |
| R10 | Тяга на ×4 и ×6 | Δv за заданное время = ×1 в допуске (Циолковский) |
| R11 | Игрок в кабине/сидит/EVA на ×6, fps 10/30/60 | не «теряется», позиция относительно корабля консистентна |

- Логика таймлайна (R5 + сценарии перезаписи) — модульные тесты в

- Runtime-проверки (R4, R7–R11) — через Unity-мост (`unity status` → порт 7800),

## 10. Отклонения (обязательный список в отчёте)

1. Перемотка = восстановление снимка, не обратная интеграция.
2. В контактной зоне откат запрещён (кроме точки 0 через билдер), точки в зоне серые.
3. Выше ×6 модель меняется: баллистика без тяги и сопротивления (проверяется формально).
4. Атмосфера/посадка: эффективный фактор ≤×3.
5. Темп на ×10⁵…×10⁶ у планеты ограничен бюджетом кадра.
6. Переключатели (SAS, РСУ, двигатели) и газ откатываются; физическое удержание клавиш — живой ввод и не восстанавливается.
7. Сетка точек по реальному времени, в модельном неравномерна.
8. Всё, что решено иначе, чем в этом файле, — с причиной.
